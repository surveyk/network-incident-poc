# Network Incident PoC — Web UI Specification

## 1. 목적

본 문서는 Network Incident PoC의 Web 화면 구성과 사용자 인터페이스 기준을 정의한다.

Web UI의 목적은 네트워크 기술 로그를 많이 보여주는 것이 아니다.

관리자 또는 운영자가 다음 정보를 빠르게 파악할 수 있도록 하는 것이 목적이다.

- 어디에서 장애가 발생했는가
- 어떤 업무에 영향 가능성이 있는가
- 업무 중요도는 어느 정도인가
- 복구 우선순위는 무엇인가
- 현재 복구상태는 어떠한가
- 장애경과는 어떻게 진행되었는가
- 어떤 원인을 우선 검토할 수 있는가
- 무엇을 추가로 확인해야 하는가

---

# 2. Web UI 기본 방향

기본 화면은 Dashboard보다 **장애 상황보고서** 형태를 우선한다.

화면구성 원칙:

```text
관리자용 핵심정보
↓
장애경과
↓
조치내용
↓
추정원인 및 추가확인
↓
기술 상세정보
```

화려한 그래프나 복잡한 네트워크 Topology를 기본 화면에 표시하지 않는다.

---

# 3. 사용자 대상

주요 사용자는 다음과 같다.

```text
네트워크 운영 담당자
정보화 담당자
상황관리자
관리자 / 보고자
```

네트워크 전문지식이 없는 관리자도 내용을 이해할 수 있어야 한다.

---

권장 화면:

---

# 5. 화면 상단

화면 상단에는 다음 정도만 표시한다.

```text
Network Incident PoC

네트워크 장애 상황보고
```

필요하면 다음 상태를 추가할 수 있다.

```text
분석 완료
AI 분석 완료
AI 분석 사용 불가
```

과도한 Header 메뉴는 만들지 않는다.

---

# 6. 장애 요약 영역

첫 화면에서 가장 중요한 영역이다.

표시항목:

```text
발생일시
최초 이상징후
장애구간
영향 가능 업무
업무 중요도
복구 우선순위
현재상태
반복 장애 여부
```

권장 구성:

```text
┌ 장애 요약 ──────────────────────────────┐

발생일시        2026.9.30. 10:21:24 ~ 10:22:13
최초 이상징후   10:21:02
장애구간        2층 네트워크

영향 가능 업무  112시스템, 온나라, 폴넷

업무 중요도     매우 높음
복구 우선순위   P1 / 최우선
현재상태        복구 완료
반복 장애 여부  확인 필요

└──────────────────────────────────────────┘
```

---

# 7. 영향업무 표현

실제 서비스 장애가 확인되지 않은 경우 반드시 다음 표현을 사용한다.

```text
영향 가능 업무
```

또는:

```text
업무영향(확인 필요)
```

다음 표현은 사용하지 않는다.

```text
112시스템 장애
온나라 장애
TCS 장애
```

별도 서비스 상태 확인정보가 있을 때만 실제 장애 표현을 사용할 수 있다.

---

# 8. 중요도 및 우선순위 표시

내부값보다 사용자 친화적인 표시값을 우선한다.

예:

```text
VERY_HIGH
→ 매우 높음

P1
→ P1 / 최우선

RECOVERED
→ 복구 완료
```

내부값만 단독으로 크게 보여주지 않는다.

---

# 9. 장애경과 영역

A의 Timeline을 표시한다.

권장 형태는 단순 시간순 목록이다.

예:

```text
10:21:02
MAC 주소 반복 이동 감지

10:21:22
2층 방향 Broadcast 증가

10:21:24
2층 네트워크 연결 중단

10:22:05
장애 의심 포트 차단

10:22:13
2층 네트워크 연결 복구
```

복잡한 Timeline Library는 1일 PoC에서 사용하지 않아도 된다.

---

# 10. Timeline 표시원칙

Timeline에는 관리자에게 필요한 핵심 이벤트만 표시한다.

표시하지 않아도 되는 정보:

```text
모든 CPU 값
모든 Interface 상태
모든 정상 이벤트
전체 Raw Log
```

기술 세부정보는 상세영역에서 제공한다.

---

# 11. 단계 표시

필요하면 Timeline에 단계 표시를 추가할 수 있다.

예:

```text
[이상징후] 10:21:02
MAC 주소 반복 이동

[장애] 10:21:24
2층 네트워크 연결 중단

[조치] 10:22:05
장애 의심 포트 차단

[복구] 10:22:13
2층 네트워크 연결 복구
```

영문 `PRECURSOR`, `INCIDENT`를 그대로 보여주기보다 한글 표현을 우선한다.

---

# 12. 조치내용 영역

A Timeline의 `ACTION`과 이후 복구이벤트를 이용한다.

예:

```text
조치내용

- 장애 의심 포트 차단
- 조치 이후 2층 네트워크 연결 복구
- Broadcast 및 장비 상태 정상화 확인
```

향후 확인할 사항은 여기에 표시하지 않는다.

---

# 13. 추정원인 영역

AI가 정상적으로 동작한 경우 표시한다.

예:

```text
추정원인

현재 로그 흐름에서는
2층 내부 L2 Loop 가능성을 우선 검토할 수 있습니다.
```

다음과 같이 확정적으로 표현하지 않는다.

```text
장애원인: L2 Loop
```

---

# 14. 주요 근거

추정원인 바로 아래 핵심근거를 표시할 수 있다.

예:

```text
주요 근거

- MAC 주소 반복 이동
- Loop 관련 이벤트
- Broadcast 증가
- 의심 포트 차단 이후 정상화
```

2~4개 정도를 기본으로 한다.

---

# 15. 확인 한계

AI 분석의 불확실성을 별도 표시한다.

예:

```text
확인 한계

실제 물리적 연결상태와 전체 VLAN 구성이 확인되지 않아
최종 장애원인 확정을 위해 추가 점검이 필요합니다.
```

이를 통해 추정과 확정을 구분한다.

---

# 16. 추가확인 영역

담당자가 다음으로 확인해야 할 항목을 표시한다.

예:

```text
추가확인

- 장애 의심 포트 실제 연결상태 확인
- VLAN 구성 확인
- 112시스템 실제 서비스 정상 여부 확인
- 동일 구간 유사 장애이력 확인
```

조치내용과 구분한다.

---

# 17. AI 상태 표시

AI 상태는 필요할 경우 간단하게 표시한다.

정상:

```text
AI 분석 완료
```

실패:

```text
AI 분석 사용 불가
```

오류 상세 메시지를 관리자 화면에 길게 표시하지 않는다.

---

# 18. AI 실패 화면

Azure OpenAI가 실패해도 화면 전체는 정상적으로 유지한다.

예:

```text
장애 요약
정상 표시

장애경과
정상 표시

조치내용
정상 표시

추정원인 및 추가확인
AI 분석을 사용할 수 없습니다.
```

A Core 기반 정보는 그대로 제공한다.

---

# 19. 기술 상세정보

관리자용 본문 하단에 접기/펼치기 형태로 제공한다.

예:

```text
▶ 기술 상세정보
```

펼치면:

```text
분석 장비
관련 Event
Fact
source_line
analysis_context
```

등을 표시한다.

---

# 20. Fact 표시

기술 상세정보에서는 다음 형식으로 표시할 수 있다.

```text
10:21:02
2층 층간스위치

MAC 주소 반복 이동이 확인됨

원본 로그 위치: Line 4
```

Fact와 AI 추정을 시각적으로 분리한다.

---

# 21. Analysis Context 표시

기술 상세 영역에 다음 정보를 표시할 수 있다.

예:

```text
분석 장비
- 2층 층간스위치
- 백본스위치

분석 장비 수
2대

관련 이벤트
17건
```

관리자 본문에는 기본 표시하지 않는다.

---

# 22. Raw Log

전체 Raw Log는 관리자 기본화면에 표시하지 않는다.

필요한 경우 기술 상세화면에서 제한적으로 보여줄 수 있다.

PoC에서는 Raw Log 전체 조회 기능을 구현하지 않아도 된다.

Fact의 `source_line` 표시만으로도 충분하다.

---

# 23. 화면 폭

Desktop 환경을 기본으로 한다.

권장:

```text
중앙 정렬
최대 폭 약 1000~1200px
```

너무 넓게 펼쳐진 Dashboard보다 문서 형태를 유지한다.

---

# 24. 화면 디자인

디자인 원칙:

```text
흰색 배경
단순한 테두리
충분한 여백
표와 문단 중심
명확한 제목 계층
```

과도한 색상 사용을 피한다.

---

# 25. 상태 강조

필요하면 중요 상태만 제한적으로 강조한다.

예:

```text
P1 / 최우선
복구 완료
AI 분석 사용 불가
```

모든 필드에 Badge를 사용하지 않는다.

---

# 26. Font / 가독성

한글 가독성을 우선한다.

특정 외부 Web Font를 필수로 사용하지 않는다.

운영환경에서 사용 가능한 기본 시스템 Font를 우선한다.

---

# 27. Web Framework

1일 PoC에서는 복잡한 Front-end Framework를 사용하지 않는다.

권장:

```text
FastAPI
+
Jinja2
+
HTML
+
간단한 CSS
```

React, Vue 등 별도 SPA Framework는 기본적으로 사용하지 않는다.

---

# 28. Backend 역할

`src/app.py`는 다음 역할만 담당한다.

```text
요청 수신
↓
A 또는 Mock Core 호출
↓
AI Adapter 호출
↓
Report Builder 호출
↓
Template Rendering
```

Business Logic을 `app.py`에 과도하게 넣지 않는다.

---

# 29. Report Builder 사용

Web Template은 A JSON과 AI JSON을 직접 복잡하게 해석하지 않는다.

권장:

```text
A Core
+
AI Result
↓
Report Builder
↓
View Model
↓
HTML Template
```

Template은 화면 표시만 담당한다.

---

# 30. 기본 Route

PoC에서는 하나의 기본 Route로 충분하다.

예:

```text
/
```

처리:

```text
Golden Sample
↓
분석 결과
↓
관리자 보고서
```

필요하면 이후 다음 정도를 추가할 수 있다.

```text
/detail
```

그러나 1일 PoC에서는 단일 Page도 충분하다.

---

# 31. 입력 방식

D-Day Demo에서는 다음 중 가장 단순한 방식 하나를 선택한다.

## 방법 A

고정 Golden Sample 사용

```text
loop_2f.log
```

## 방법 B

로그파일 Upload

```text
.log 파일
↓
분석
↓
결과
```

시간 여유가 없다면 방법 A를 우선한다.

파일 Upload는 부가기능으로 취급한다.

---

# 32. 추천 Demo 방식

가장 안정적인 Demo 흐름:

```text
[2층 Loop Sample 분석]
          ↓

장애 상황보고 출력
          ↓

기술 상세정보 확인
```

Demo 중 외부 기능을 많이 클릭할 필요가 없게 한다.

---

# 33. 1층 / 3층 결과

1층과 3층 Validation Sample도 Web에서 표시 가능해야 한다.

단, 모든 Sample을 메인 UI에서 선택하는 기능까지 반드시 만들 필요는 없다.

통합테스트로 검증하면 충분하다.

시간이 허용되면:

```text
Sample 선택
1층 / 2층 / 3층
```

기능을 추가할 수 있다.

필수기능은 아니다.

---

# 34. 오류 처리

사용자에게 Python Traceback을 직접 보여주지 않는다.

예:

```text
분석 중 오류가 발생했습니다.
입력 로그 또는 시스템 상태를 확인해주세요.
```

개발용 로그에는 상세 오류를 기록할 수 있다.

---

# 35. Core 오류와 AI 오류 구분

Core 처리 실패:

```text
장애 분석 실패
```

AI만 실패:

```text
장애 분석 결과는 정상
AI 원인분석만 사용 불가
```

두 상황을 동일하게 처리하지 않는다.

# 43. 최종 원칙

Web UI의 목적은 기술적인 로그를 많이 보여주는 것이 아니다.

최종 목표는:

> 관리자가 장애 위치, 업무영향, 복구 우선순위, 장애경과 및 원인 후보를 한 화면에서 빠르게 이해할 수 있도록 하는 것

이다.

따라서 화면은 Dashboard가 아니라 **판단지원용 장애 상황보고서**를 중심으로 구성한다.
